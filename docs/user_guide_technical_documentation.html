Flask AI Chat Application

A step-by-step guide to how this project was built, from an empty folder to a live website with real user accounts, an AI chatbot, and a live analytics dashboard. Written in plain language — no assumed experience needed.

What you'll find in this guide → Setting up the project from scratch → Connecting the app to real AI models → How the database is organized → Adding real user accounts → Putting the app on the internet → Building a live analytics dashboard → How to actually use the finished app

What this app does

It's an AI chat application — similar to ChatGPT — where a person creates an account, signs in, and has conversations with an AI. Behind the scenes it:

  • Talks to two different AI providers (OpenAI and Google Gemini) — if one is unavailable, it automatically tries the other, so the chat keeps working
  • Saves every conversation to a real database, encrypted so the raw text can't be read by anyone browsing the database directly
  • Lets people sign up with an email and password, or sign in with their Google account
  • Shows a sidebar of past conversations, like ChatGPT does
  • Tracks its own usage and errors, and feeds that into a live dashboard built in Power BI
  • Runs live on the internet — anyone with the link can try it

Setting Up the Project

Download it from python.org, or on Windows, open a terminal and run:

winget install Python.Python.3.12

Confirm it installed correctly:

python --version

2Create the project folder

Open a terminal and run:

mkdir flask-chatgpt-app
cd flask-chatgpt-app

Open this folder in VS Code (File → Open Folder).

Virtual Environment

A virtual environment keeps this project's Python packages separate from everything else on the computer. In the VS Code terminal:

python -m venv venv

Then activate it. On Windows (Git Bash):

source venv/Scripts/activate

You'll know it worked when (venv) appears at the start of the terminal line.

The Basic Flask App

Every Flask app starts the same simple way. Create a file called app.py:

from flask import Flask

app = Flask(__name__)

@app.route('/')
def home():
    return "Welcome to the app!"

if __name__ == '__main__':
    app.run(debug=True)

Run it:

python app.py

Then open http://127.0.0.1:5000 in a browser — that's the app, running locally on the computer.

Connecting the AI

To make the chat actually talk to an AI, the app needs an API key from the provider. This project uses two: OpenAI and Google Gemini.

Getting API keys

  • OpenAI: create a key at platform.openai.com/api-keys (requires adding a small amount of billing — a ChatGPT subscription does not cover API usage, they're billed separately)
  • Gemini: create a free key at aistudio.google.com/apikey — Google's free tier needs no billing card

Storing keys safely

API keys are secrets — they should never be typed directly into the code. Instead, they go in a separate file called .env, which is never uploaded anywhere:

OPENAI_API_KEY=your_real_key_here
GEMINI_API_KEY=your_real_key_here

The code then reads them like this:

from dotenv import load_dotenv
import os

load_dotenv()
openai_api_key = os.environ.get("OPENAI_API_KEY")
Important: a file called .gitignore must list .env so it's never accidentally uploaded to GitHub. This is set up in the Git & GitHub section.

Automatic Fallback Between AI Providers

Rather than relying on a single AI provider (which could run out of credits, hit a rate limit, or have an outage), the app tries OpenAI first, and automatically switches to Gemini if that fails — the person chatting never sees an error, they just get an answer.

def get_ai_reply(user_message):
    try:
        response = openai_client.chat.completions.create(
            model="gpt-5.6-luna",
            messages=[{"role": "user", "content": user_message}],
            max_tokens=150
        )
        return response.choices[0].message.content.strip(), "openai"
    except Exception:
        pass  # fall through to Gemini below

    response = gemini_client.models.generate_content(
        model="gemini-3.5-flash-lite",
        contents=user_message
    )
    return response.text.strip(), "gemini"

The app also remembers which provider actually answered each message ("openai" or "gemini") — this becomes useful later for the analytics dashboard.

Database

Installing PostgreSQL

The app needs somewhere to actually store accounts and messages permanently — that's what a database is for. This project uses PostgreSQL, a free, widely-used database.

  1. Download the installer from postgresql.org
  2. Run it, keeping the default options
  3. Set (and remember) a password for the postgres superuser
  4. Keep the default port, 5432
  5. pgAdmin is installed automatically alongside it — this is the visual tool used to look inside the database

Once installed, open pgAdmin, connect using the password from step 3, then create a new database (right-click Databases → Create → Database) and name it flask-chat-app.

Connecting the App to the Database

Flask talks to the database through a library called SQLAlchemy. This connection string tells it where the database lives and how to log in:

DB_PASSWORD = os.environ.get("DB_PASSWORD")
app.config['SQLALCHEMY_DATABASE_URI'] = (
    f'postgresql://postgres:{DB_PASSWORD}@localhost:5432/flask-chat-app'
)
db = SQLAlchemy(app)

The database password is another secret — it also lives in .env, never written directly in the code.

How the Database is Organized

The database holds four separate tables, each with one clear job:

user — holds accounts

One row per person: their email, a scrambled (hashed) version of their password, and a Google account ID if they signed in that way.

chat_message — holds conversations

Every message, tagged with which conversation it belongs to and which AI answered. The actual message text is encrypted — see the Encryption section.

request_log — holds usage statistics

A lightweight record of every chat request: how long it took, which AI answered, whether it succeeded, and a rough category of what it was about. This table has no actual message content in it at all — it's specifically designed to be safe to connect analytics tools to directly.

error_log — holds real bugs

If something genuinely breaks in the app, the details get logged here automatically — feeding a live "bug report" view in the dashboard.

Splitting the data this way means the analytics dashboard (Power BI) can read real usage numbers without ever being able to see anyone's actual conversations — because it only ever connects to request_log and error_log, never chat_message.

Encrypting Messages

Chat messages are scrambled before they're saved to the database, using a method called Fernet encryption. Anyone looking directly at the database — even someone with full access to it — sees only unreadable text like gAAAAABq..., not the real conversation.

First, a one-time secret key is generated:

python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"

That key goes into .env as ENCRYPTION_KEY. The app then uses it to scramble messages on the way in, and unscramble them on the way back out — only the app itself (holding that key) can do the unscrambling:

def encrypt_text(plain_text):
    return fernet.encrypt(plain_text.encode()).decode()

def decrypt_text(encrypted_text):
    return fernet.decrypt(encrypted_text.encode()).decode()
This key must never be lost. If it's lost, every previously saved message becomes permanently unreadable — that's the nature of real encryption.

User Accounts

Email & Password Login

Real passwords are never stored — only a one-way scrambled version (a "hash"), so even someone with full database access can't see anyone's actual password.

from werkzeug.security import generate_password_hash, check_password_hash

new_user = User(email=email, password_hash=generate_password_hash(password))

Signing in checks the typed password against that hash, without ever storing or revealing the real one:

if check_password_hash(user.password_hash, password):
    login_user(user)

Google Sign-In

Instead of a password, someone can sign in using their existing Google account. This uses a standard, secure handshake called OAuth — the app never sees or handles the person's actual Google password.

  1. Create a project at console.cloud.google.com
  2. Under APIs & Services → Credentials, create an OAuth client ID (type: Web application)
  3. Add the app's real web address as an Authorized redirect URI, e.g. https://your-app.onrender.com/login/google/callback
  4. Copy the generated Client ID and Client Secret into .env

When someone clicks "Sign in with Google," the app sends them to Google, they approve access, and Google redirects them back with confirmation of who they are — the app then either finds their existing account or creates a new one automatically.

Frontend

The Chat Interface

The chat screen is a single page: a message list that scrolls, and a text box with a Send button that stays fixed at the bottom — the same layout pattern used by ChatGPT and similar apps. Every message the person sends, and every reply, becomes its own message "bubble":

function appendMessage(role, text) {
    const bubble = document.createElement('div');
    bubble.className = 'bubble ' + role; // 'user' or 'assistant'
    bubble.textContent = text;
    document.getElementById('chat-log').appendChild(bubble);
}

While waiting for a reply, a temporary "Thinking…" bubble shows, then gets replaced once the real answer comes back.

Sidebar & Conversation History

Every conversation is given its own ID. Messages are grouped by that ID, so the sidebar can list past conversations, and clicking one loads its messages back into view — again, the same pattern ChatGPT uses.

  • + New Chat — starts a fresh conversation ID
  • Clicking a past conversation — loads that conversation's messages from the database (decrypting them on the way)
  • The sidebar can collapse on desktop, and slides in/out as an overlay on mobile

Mobile Responsive Design

The layout adjusts automatically for smaller screens using CSS media queries — rules that only apply below a certain screen width:

@media (max-width: 768px) {
    .sidebar {
        position: fixed;
        transform: translateX(-100%); /* hidden by default */
    }
    .sidebar.open {
        transform: translateX(0); /* slides in when opened */
    }
}

A floating menu button appears only on small screens, since the sidebar is hidden off-screen until it's tapped open.

One real-device detail worth knowing: mobile browsers hide/show their address bar as someone scrolls, which changes how much screen is actually visible. Using dvh (dynamic viewport height) instead of the older vh unit accounts for this, so nothing important ends up hidden below the visible screen.

Monitoring

Usage Logging

Every time someone sends a message, the app quietly records a few facts about that request — not the message itself, just the metadata: how long it took, which AI answered, whether it succeeded, and a rough topic category (worked out from simple keyword matching, not real AI classification).

db.session.add(RequestLog(
    user_id=current_user.id,
    conversation_id=conversation_id,
    model_used=source,
    success=True,
    response_time_ms=response_time_ms,
    category=category
))

This is what later powers the Power BI dashboard's usage numbers.

Error Logging

If something genuinely goes wrong anywhere in the app — a bug, an unexpected failure — it gets caught and logged automatically, including the type of error and the technical details, so it can be reviewed later.

@app.errorhandler(Exception)
def handle_unexpected_error(e):
    if isinstance(e, HTTPException):
        return jsonify({'error': e.description}), e.code  # ignore routine 404s etc.

    log_error(
        endpoint=request.path,
        error_type=type(e).__name__,
        error_message=traceback.format_exc()
    )
    return jsonify({'error': 'Something went wrong on our end.'}), 500

Routine things like a mistyped web address (a normal "404 Not Found") are deliberately not logged as bugs — only genuine code problems are, so the error log stays meaningful instead of filling up with noise.

Version Control

Git & GitHub Setup

Git keeps a full history of every change made to the code. GitHub is where that history is stored online — this project uses a private GitHub repository, so only the owner can see it.

What never gets uploaded

A file called .gitignore tells Git which files to always skip — critically, this includes .env (real secrets), the venv folder (huge, and rebuildable by anyone), and any raw database exports.

venv/
__pycache__/
.env
local_backup.dump
*.sql

First-time setup

git init
git add .
git commit -m "Initial commit"

Then create a new, private repository on GitHub, and connect it:

git remote add origin https://github.com/yourusername/flask-chatgpt-app.git
git branch -M main
git push -u origin main
GitHub no longer accepts your account password for this. Instead, create a Personal Access Token (Settings → Developer settings → Personal access tokens) and use that in place of a password when prompted — or use GitHub's built-in Credential Manager, which handles login through a browser popup automatically.

Pushing Future Updates

After the first setup, updating the code online is just three commands, run any time something changes:

git add .
git commit -m "describe what changed"
git push

Going Live

Cloud Database (Neon)

The database running on a personal computer can't be reached by the outside internet — so a live, public version of the app needs a database that lives online too. This project uses Neon, a free, cloud-hosted PostgreSQL service.

  1. Sign up free at neon.tech
  2. Create a new project — Neon gives back a connection string, e.g. postgresql://user:pass@host/dbname?sslmode=require
  3. Copy the existing local data across using two commands:
# Export from the local database
pg_dump -h localhost -U postgres -d flask-chat-app -F c -f local_backup.dump

# Import into Neon
pg_restore --no-owner --no-privileges -d "your-neon-connection-string" local_backup.dump

Running two databases at once, safely

The code automatically detects which environment it's running in, and picks the right database — no manual switching required:

if os.environ.get("RENDER"):
    # Live on Render — always use the cloud database
    app.config['SQLALCHEMY_DATABASE_URI'] = os.environ.get("DATABASE_URL")
else:
    # Running on a personal computer — always use the local database
    app.config['SQLALCHEMY_DATABASE_URI'] = f'postgresql://postgres:{DB_PASSWORD}@localhost:5432/flask-chat-app'

RENDER is a variable Render sets automatically on any app it hosts — it's simply never present on a personal computer, which is what makes this switch fully automatic.

Deploying to Render

Render is a free hosting service that runs the app continuously online, rebuilding it automatically every time new code is pushed to GitHub.

  1. Sign up at render.com
  2. New + → Web Service → connect the GitHub repository
  3. Build Command: pip install -r requirements.txt
  4. Start Command: gunicorn app:app
  5. Add every secret from .env as an Environment Variable in Render's dashboard (real values, no quote marks around them)
  6. Click Create Web Service
Free tier note: the live app "falls asleep" after about 15 minutes without visitors, and takes up to a minute to wake back up on the next visit. This is a standard tradeoff of free hosting, not a bug — worth knowing if sharing the link with someone.

Don't forget: Google Sign-In needs the live address too

Once the live web address exists (e.g. https://flask-chatgpt-app.onrender.com), it must also be added as a second Authorized redirect URI in Google Cloud Console, alongside the existing localhost one — both stay listed together, so login works in both places at once.

Analytics Dashboard

Connecting Power BI

Power BI Desktop connects directly to the database and displays live charts built from real usage data. Two separate files are kept — one pointed at the local database (for testing), one pointed at Neon (showing real, live activity).

  1. Get Data → PostgreSQL database
  2. Enter the server address and database name
  3. Choose DirectQuery mode — not Import — so the dashboard queries live data every time, instead of a one-time snapshot
  4. Select only the request_log and error_log tables — never chat_message, since its content is encrypted and unreadable to Power BI anyway
For a local Postgres connection, "Use encrypted connection" should be unchecked (a local database has no SSL set up). For Neon, this isn't an issue — Neon requires encryption automatically.

Building the Dashboard

The dashboard is organized into pages, each answering a different question about the app:

PageShows
Executive OverviewTotal conversations, messages, active users, average response time, error rate, usage over time
Model AnalyticsHow OpenAI vs Gemini are performing — which one is actually answering, and how fast
CategoriesWhat people are asking about most, by rough topic
System Health / Bug ReportSuccess and error rates, plus a live table of any real errors that occurred

Each number on the page is a small formula called a measure, for example:

Total Conversations = DISTINCTCOUNT('public request_log'[conversation_id])
Active Users = DISTINCTCOUNT('public request_log'[user_id])
Error Rate = COALESCE(DIVIDE(
    CALCULATE(COUNTROWS('public request_log'), 'public request_log'[success] = FALSE),
    COUNTROWS('public request_log')
), 0)

Making It Auto-Refresh

By default, Power BI only updates when someone manually clicks Refresh. Turning on Automatic Page Refresh makes it re-check the database on its own, every few seconds:

  1. Click an empty area of the report page (not on any chart)
  2. In the Format panel, find Page refresh and turn it on
  3. Set the refresh type to Fixed interval, e.g. every 10 seconds
Honest limitation: this only works while Power BI Desktop is open on the person's own computer — it isn't a public, always-on dashboard other people can open in a browser. Making it fully public and always-live would need Power BI Service with a paid license, a separate step beyond this project's current scope.

Using the App

This section is for anyone using the finished app — no technical background needed.

Creating an Account

  1. Open the app's web address
  2. Choose one of two ways to sign in:
    • Email & password — click "Don't have an account? Sign up," enter an email and a password (at least 8 characters)
    • Google account — click "Sign in with Google" and approve on Google's screen
  3. Once signed in, the chat screen opens automatically

Using the Chat

  1. Type a message in the box at the bottom and press Send (or hit Enter)
  2. The AI's reply appears a moment later, above the input box
  3. Keep the conversation going by simply typing another message
As with any AI, replies can occasionally be wrong or inaccurate — always double-check anything important, and never share sensitive, personal, or confidential information in the chat.

Managing Conversations

  • Starting a new topic? Click + New Chat in the sidebar — this begins a fresh conversation without losing the old one
  • Returning to an old conversation? Click it in the sidebar list to load it back
  • On a phone? Tap the menu icon (☰) to open the sidebar; it closes automatically after picking something
  • Signing out? Click Log out at the bottom of the sidebar
